## Recovery and stop conditions

- Old production copies are separate archives, not a rollback target or compatibility requirement. Do not reconnect the old worker or restore old state into the new production runtime.
- On failure, stop and preserve the new state. Recover using the new production seed, backups, fixed bundles, and existing retry operations. Ask before any restore or reset that could discard new approvals or make the database disagree with Git.
- Stop for an unverifiable backup, missing seed provenance, changed remote opinion files, mismatched deployed SHA, unexpected evidence overlap, failed validation/push, or missing production tracing. Preserve state rather than reset it.
- A stopped new batch uses existing recovery and retry commands against its fixed bundle. Failure is acceptable; evidence duplication or an unreviewed reset is not.
