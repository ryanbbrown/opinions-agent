# Braintrust Opinion Evals Plan

## Goal

Set up a proper eval workflow for the opinion agent using Braintrust. The eval should run the agent on week-level cases, capture generated proposals and trace behavior, compare the results against structured targets from `EVAL_TARGETS.md`, and upload experiments/traces to Braintrust.

## Braintrust Primitives

Braintrust supports the workflow we need:

- Datasets use `input`, `expected`, `metadata`, and `tags`.
- Experiments run through `Eval()` as `data + task + scores`.
- Scorers can be LLM-as-judge or custom code.
- Trace-level scorers can inspect the full trace for agent behavior.

Relevant docs:

- https://www.braintrust.dev/docs/annotate/datasets
- https://www.braintrust.dev/docs/evaluate/run-evaluations
- https://www.braintrust.dev/docs/evaluate/write-scorers
- https://www.braintrust.dev/docs/integrations/sdk-integrations/opentelemetry

## Dataset Shape

Use one dataset row per week, not one row per opinion. The agent produces a batch of proposals, so scoring should judge the whole batch.

Example row:

```json
{
  "input": {
    "week": "W08",
    "opinions_seed": "canonical-through-W07",
    "selected_evidence": [
      {
        "evidence_id": "rw:...",
        "title": "Being Someone who Does Things",
        "text": "..."
      }
    ]
  },
  "expected": {
    "targets": [
      {
        "target_id": "W08-03",
        "ideal_opinion": "Passive productivity like reading and podcasts is helpful...",
        "required_sources": ["rw:..."]
      }
    ],
    "not_converted": [
      {
        "evidence_id": "rw:...",
        "title": "Learn In Public"
      }
    ]
  },
  "metadata": {
    "week": "W08",
    "source_file": "EVAL_TARGETS.md"
  }
}
```

## Structured Target Data

`EVAL_TARGETS.md` is the single source of truth for targets (`EVAL_SET.md` is stale and unused): verified opinions, sources, and not-converted lists. Convert it as-is into a structured checked-in file, probably `eval/opinion_targets.jsonl` or YAML.

Per-opinion key-points bullets are deliberately not part of the first pass: a generated draft mostly restated each opinion sentence and added little judge signal (draft preserved in `EVAL_TARGETS_KEY_COMPONENTS.md` for reference). Instead, run the judge against the ideal opinion text and sources, review where its verdicts disagree with Ryan's, and add targeted per-opinion guidance only where disagreements show it is needed.

## Week Seed State

Eval weeks must be independent and reproducible, so each week runs against a canonical per-week snapshot rather than the output of prior eval runs:

- Week W's seed `OPINIONS.md` is the base file plus the canonical target opinions from all earlier eval weeks, generated by a script from the structured targets file.
- `OPINIONS_SOURCES.jsonl` is derived from the seeded inline opinions the same way sample sessions already derive it.
- Do not run weeks sequentially against agent-modified state. The first eval scope stops before approvals, so nothing would accumulate anyway without auto-approving agent output — and auto-approving would make week N's case depend on agent noise from earlier weeks and prevent single-week runs.

Each week should include:

- `week`
- selected evidence rows
- expected opinion targets
- ideal opinion text
- required source evidence IDs
- optional expected category or category family
- evidence that should not be converted into opinions

## Scorers

Use several small scorers instead of one large judge.

### `evidence_recall`

Deterministic. Evidence conversion is a classification task: ground truth labels each selected highlight as converted (it backs a canonical opinion) or not converted, and we compare that against which evidence IDs the agent cited in its proposals.

`evidence_recall` is the fraction of ground-truth-converted evidence IDs that appear in at least one generated proposal.

### `evidence_precision`

Deterministic. Of the evidence IDs the agent cited in proposals, the fraction that ground truth also converts. Every not-converted highlight that leaks into a proposal counts against this score.

### `opinion_quality`

LLM-as-judge. Compares the generated opinion to the ideal opinion and its source evidence.

Pairing generated proposals with target opinions requires a matching step: evidence overlap first, with a small LLM classifier resolving ambiguous matches. Matching is infrastructure for the judge, not a scored metric.

The judge should evaluate:

- Does the generated opinion preserve the central claim of the ideal opinion?
- Does it avoid changing the claim?
- Does it avoid over-consolidation?
- Does it preserve important examples, mechanisms, numbers, caveats, and named terms?
- Is wording difference acceptable?

Calibrate the judge by disagreement: run it, review its verdicts against Ryan's own judgment, and add targeted per-opinion guidance only where the judge gets it wrong.

Default the judge to a Claude model routed through the Braintrust proxy, so no separate OpenAI key is needed.

### `trace_read_policy`

Deferred. Deterministic trace scorer. Checks whether the agent read the source document when expected and avoided unnecessary reads when not expected.

This should inspect trace/tool activity rather than the final output.

Possible labels:

- `none`: selected evidence was sufficient; no source read expected.
- `bounded`: surrounding context or bounded file read expected.
- `full`: full document read expected.
- `optional`: source read is acceptable but not required.

Picking this up requires adding per-target expected-read labels to the targets file and deciding whether it scores strict pass/fail or partial credit.

### `section_quality`

Later scorer. Checks whether opinions are placed under useful categories.

This can start as a weak LLM/classifier scorer, then become more deterministic once expected categories stabilize.

## Trace Requirements

Thinharness always writes full-capture local JSONL traces (messages, tool args, tool results — hardcoded on for the local sink), while external OTLP sinks default to structure-only. For the Braintrust sink, set `capture_messages=True`, `capture_tool_args=True`, and `capture_tool_results=True` so Braintrust traces carry the same detail as local ones. This sends prompts and document contents to Braintrust, which is intended.

When the deferred `trace_read_policy` scorer lands, it parses the run's local JSONL trace for tool spans (tool name plus `read` path/range arguments) — same data as Braintrust holds, without an API round-trip.

Braintrust can ingest OpenTelemetry traces with:

```bash
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://api.braintrust.dev/otel/v1/traces
OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer <key>, x-bt-parent=project_id:<project_id>"
```

Add Braintrust tracing config using:

- `BRAINTRUST_PROJECT_ID`
- `BRAINTRUST_API_KEY`

This replaces the Langfuse hook: remove the Langfuse settings and `make_langfuse_tracing`. All tracing goes to Braintrust going forward. Separate run types from the start: eval runs land as experiments, and any dev/production runs land as logs in the same single Braintrust project, stamped with an `environment` metadata tag (`dev`/`prod`). The tracing hook sets the tag from a setting that defaults to `dev` locally and `prod` on Railway (keyed off the existing `RAILWAY_VOLUME_MOUNT_PATH` detection, overridable via env var).

## Eval Execution Model

Braintrust-native but locally executed: `bt eval` runs the task function (the agent on sample sessions) and the scorers on this machine, and streams the experiment — inputs, outputs, scores, traces, metadata — to Braintrust as it runs. The agent must execute locally anyway because it needs the corpus, sample sessions, and git checkouts. Everything you look at lives in Braintrust: experiment comparison, score regressions, trace drill-down.

The checked-in structured targets file stays the reviewed source of truth, and the eval syncs it to a Braintrust dataset so cases are browsable in the UI and usable in playgrounds.

## Implementation Pieces

1. Add dependencies.

   Likely:

   - `braintrust`
   - `autoevals`
   - maybe `openai` (autoevals' client library; judge calls route through the Braintrust proxy)

2. Add config fields.

   Add settings for:

   - `BRAINTRUST_PROJECT_ID`
   - `BRAINTRUST_API_KEY`

3. Add Braintrust tracing.

   Add `make_braintrust_tracing()` in `src/opinions_agent/tracing.py`.

   Wire it into `build_harness_config()`. Remove the Langfuse hook and its settings.

4. Add structured eval targets.

   Convert `EVAL_TARGETS.md` as-is into `eval/opinion_targets.jsonl` or YAML. Sync the structured file to a Braintrust dataset; the checked-in file remains the source of truth.

5. Add proposal extraction.

   Parse the canonical Telegram HTML proposal format from the agent's initial messages:

   - extract title, proposal ID, section, opinion text, evidence IDs, and proposal type.

   Do not add eval-only structured output to the production agent contract. The `opinion_proposals` DB table exists in the schema but nothing in the app writes or reads it; if proposal persistence is ever added for product reasons, the eval can switch to reading it instead of parsing HTML.

6. Add eval runner.

   Example command:

   ```bash
   uv run opinions-agent eval run --weeks W04 W05 W06 W07 W08 W10 W11 W12 W13
   ```

   The runner should:

   - create a disposable sample session;
   - run the initial proposal phase for each target week;
   - use fake Telegram;
   - stop before approve/reject simulation;
   - collect generated proposals, selected evidence, run paths, and traces;
   - return a structured output object for Braintrust scoring.

7. Add scorers.

   Implement deterministic Python scorers for evidence recall and precision (inclusion/exclusion classification).

   Add the proposal-to-target matching helper and the LLM judge scorer for opinion quality.

8. Add Braintrust eval file.

   Example:

   ```bash
   bt eval eval/opinion_eval.py
   ```

   Or provide a CLI wrapper that calls Braintrust `Eval()` directly.

## First Eval Scope

Start with initial proposal quality only:

- run the agent on each week;
- capture initial Telegram-style proposals;
- do not simulate approve/reject/revision;
- do not validate final `OPINIONS.md` edits.

This directly measures the current optimization target:

- Did it convert the right evidence into opinions and leave the rest alone?
- Are the generated opinions faithful to the canonical ones?

Later, add a second eval for:

- source-read policy (`trace_read_policy`);
- revision behavior;
- approval application behavior;
- final artifact edits;
- category moves and final completion messages.
