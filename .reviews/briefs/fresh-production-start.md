# Fresh production start: decisions

For approval before implementation. Plan: [fresh production start](../../.plans/fresh-production-start.md). The Claude Code Fable 5.1 review is complete; `/implement` review counts still need to be selected.

## Result shape

| Responsibility | Before | After | Moves or stays |
|---|---|---|---|
| Hosting | Railway project with web and weekly cron services | Same project, services, hostname, and one Python web worker; no separate staging environment | Stays |
| Opinion generation | Old Python agent deployment | Pinned `2526a50` Python agent: candidate generation, critic, consolidator; direct OpenAI GPT-5.6 Sol at medium effort; 90-word candidate maximum | Replaced |
| Starting opinions | Previously accepted production opinions | Current checked-in pre-W04 seed plus current reviewed targets through W13, generated locally with Python | Replaced |
| Accepted artifacts | `OPINIONS.md` and `OPINIONS_SOURCES.jsonl` on the opinions repository's main branch | Same Markdown and JSONL artifacts, with the new starting content and later Telegram-approved changes | Stays |
| Evidence and document content | Reader corpus on old Railway volume | Fresh Reader sync to new Railway volume; no eval timestamp overrides | Replaced |
| Workflow and approvals | Old PostgreSQL cycles, assignments, runs, and Telegram records | Fresh PostgreSQL, owned by the Python app | Replaced |
| Agent context and ID tracking | Old decisions, memory, and allocation history | Empty decisions/memory; ID tracking starts from the new seed only | Replaced |
| Human review | Existing Telegram bot and webhook | Same bot and webhook; new messages and approvals only | Stays |
| Evals | Current Braintrust project and local disposable eval workflows | Same project, datasets, experiments, and eval baseline | Stays |
| Production traces | Shared with evals in Braintrust | Logs in a separate `opinions-agent-runs` Braintrust project | Moves |
| Scheduling | Railway weekly cron; old unfinished run blocks later weeks | Explicit sequential catch-up, then the same Monday 00:00 UTC cron | Stays after catch-up |
| Recovery | Old database, volume, and Git history | Old state kept as a separate archive; new runtime uses only its own recovery state | Separated |
| Releases | Services build from GitHub main | Explicit pinned deployments; automatic deployments remain disabled | Replaced |

## Decisions

### D1. Reuse hosting, replace runtime state
- What: Keep the existing Railway project and web/cron services. Attach fresh PostgreSQL and a fresh data volume. Use one production environment; the first real cycle is the smoke test.
- Instead of: A new project, a staging split, or continuing the old database. None is needed for the agreed clean reset.
- If wrong: The first real cycle can fail in production rather than staging. We stop and repair the new run without reviving the old runtime.

### D2. Use the current reviewed content through W13
- What: Generate the full production seed from the current local baseline and every reviewed target through W13. Expected output is 46 opinions and 94 source pairs covering 94 distinct evidence rows. Keep the app repository's checked-in pre-W04 seed unchanged for evals.
- Mechanism: Apply targets chronologically, including revisions and W13 itself; resolve full provenance from the reviewed corpus and validate every opinion and source row before publishing.
- Instead of: Copying old production opinions, copying model-generated eval proposals, or using the pre-W04 seed alone. Those do not represent the current reviewed result.
- If wrong: Production starts with missing or outdated opinions, and later proposals consolidate against the wrong content.

### D3. No compatibility with old production IDs or history
- What: Keep the IDs generated by the current eval baseline. Initialize the new allocation high-water mark from that seed only. Never import old decisions, assignments, conversations, memory, or ID limits.
- Mechanism: Write the new seed maximum to the fresh ID-tracking file before the first run. New opinions use greater IDs. Old IDs may mean something different in the separate archive.
- Instead of: Renumbering opinions or reserving IDs from old production. The user explicitly rejected those compatibility constraints.
- If wrong: An archive ID cannot safely identify an opinion in new production. The archive is not used by the new agent.

### D4. Publish only the new opinion artifacts
- What: Replace the live opinions repository's two artifacts with a normal Git commit. Preserve the old commit with an archive tag; do not add more `*_vOld` files or rewrite Git history.
- Instead of: A new opinions repository or a force-push. Keeping the repository preserves the existing destination without importing old runtime state.
- If wrong: Existing readers of the live files immediately see the reviewed baseline instead of the old production opinions.

### D5. Start after the test set and replay every later complete week
- What: Start at June 15, 2026, 00:00 UTC. Replay 12 complete weeks through September 7, 2026, 00:00 UTC. The last window is August 31–September 7. Weeks completed by old production are not considered completed here.
- Mechanism: Each weekly-cycle request selects the next seven-day window from fresh PostgreSQL progress. Finish every batch and its approved Git changes before requesting the next week. Freeze the catch-up end even if execution crosses another Monday.
- Instead of: Continuing from the old August progress marker or replaying the reviewed test set. Both contradict the agreed starting state.
- If wrong: An incorrect boundary either misses evidence or re-proposes content already in the reviewed baseline.

### D6. Use fresh Reader data, not eval runtime fixtures
- What: Fresh-sync the Reader corpus with normal source timestamps. Keep eval availability overrides, databases, run directories, and conversation state out of production.
- Mechanism: Before launch, compare fresh pre-boundary evidence with the reviewed corpus. Report new or changed pre-boundary evidence and missing timestamps before the normal launch boundary can ignore it. Ask about actual discrepancies, not a hypothetical loss.
- Instead of: Copying the local eval corpus as production truth or silently treating every old-dated row as reviewed.
- If wrong: Evidence never reviewed in the test set could be skipped. This check stops launch for a decision rather than silently dropping it.

### D7. Clear retired Telegram input before new proposals exist
- What: Reuse the bot and webhook but discard pending cutover updates. Do not resume or approve the old proposals.
- Mechanism: While no new run exists, register the webhook with `drop_pending_updates=true`, confirm the queue is empty, and only then start a new cycle. This prevents queued standalone `GO` or `SKIP` from advancing a new conversation.
- Instead of: Replaying old updates against fresh state. Old callbacks reference absent rows, but standalone commands can affect a new awaiting run.
- If wrong: Messages sent during the cutover are discarded. They belong to the retired workflow, not to new approvals.

### D8. Keep human approval and existing retry boundaries
- What: The user reviews new proposals in Telegram. The app validates, commits, and pushes approved changes. A failure retains the new run's fixed evidence bundle for inspection and retry.
- Mechanism: Use weekly-cycle starts, not manual window runs. Repeated starts return active work. Never send synthetic approvals or reset assignments to accelerate catch-up.
- Instead of: Auto-accepting weeks because similar opinions passed earlier or rebuilding a failed week's evidence from scratch.
- If wrong: Catch-up needs user attention and stops when a batch fails; it does not finish unattended.

### D9. Separate production tracing from evals
- What: Keep evals in the existing Braintrust project. Put production logs in `opinions-agent-runs`, using its UUID in the web service configuration and existing credentials.
- Instead of: Another experiment within the current project. A separate project keeps production logs out of the eval workspace.
- If wrong: Production traces are missing or still mixed with evals. Verify a real trace before continuing beyond the first cycle.

### D10. Separate merging code from deploying production
- What: A local main fast-forward is safe. Do not push to GitHub main while Railway automatic deployments are enabled. Keep the application pinned to `2526a50`; documentation and preparation tooling may use later commits without changing the deployed agent.
- Mechanism: Disable automatic deployments on both services and stop old work first. Publish and explicitly deploy the pinned revision only after fresh state and the seed are ready. Publish later documentation separately. Leave future releases manual.
- Instead of: Merging and pushing first, which could deploy new code against old pending state, or letting every documentation push replace the pinned build.
- If wrong: Source main and the deployed revision differ intentionally. Releases require an explicit deployment step.

### D11. Archive old state, recover only within the new runtime
- What: Preserve a consistent database dump, volume archive, Git refs, and protected configuration before replacement. Verify the copies. Retain old resources until cleanup approval, but never reconnect them as a rollback target.
- Mechanism: Stop the old worker before copying state and verify configuration changes cannot restart it. Fresh production receives its own backups. On failure, retain and recover the new state; ask before a restore that would discard approvals.
- Instead of: Deleting the only old copies immediately, or designing backward-compatible restoration into the new deployment.
- If wrong: Retained resources may continue to cost money until cleanup. The old archive is not an automatic production fallback.
